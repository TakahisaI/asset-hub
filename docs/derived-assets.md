# 統合と派生アセットの設計

Issue #10の設計決定。[2026-10-18の棚卸し](reports/render-load-2026-10-18.md)を先に実施した。初版のベイカー・派生schema・登録は実装済みで、[実行方法](../README.md#統合した派生アセットの登録)を参照。

## 判断と最初の対象

現在版205件では船の描画コール中央値302、建物477、小道具22。島の最大71,717コール・204,391,691描画三角形は集合体で、1隻の予算とは分ける。最初は船1隻の固定版で、剛体グループ内の材質ごとの統合がどこまでコールを減らすかを調べる。島全体の一括結合や三角形削減・テクスチャの再ベイクは最初の実装に入れない。統合で三角形数やテクスチャ容量が減るとは扱わない。

正本はそのまま保持し、ゲームが実際に読む形態を別IDの兄弟アセットとして登録する。承認状態・必須レビュー・正本の自動置換は設けない。検証結果への観察は任意の版付きメモで残す。

## レシピと識別

入力は正本IDとGLB SHA-256で固定する。`source.commit` は制作元のコミットであり、GLBの版やレシピハッシュとは別物である。GLB・必要な動作設定・生成器は既存の保存済みスナップショットを使い、元の制作リポジトリを変更しない。

`catalog/recipes/<sha256>.json` に次の形式のレシピを保存する。以下の `<...>` は型を説明するプレースホルダーで、実行可能な値ではない。

```json
{
  "schema": 1,
  "operation": "merge-rigid-material",
  "source": { "id": "ship.example", "revision": "<64桁のGLB SHA-256>" },
  "behavior": "<入力動作設定のSHA-256。動作設定がなければキーを省略>",
  "tool": {
    "repository": "TakahisaI/asset-hub",
    "commit": "<生成器の40桁コミット>",
    "scriptHash": "<生成器のSHA-256>",
    "runtime": "<Node・使用ライブラリ・OS/アーキテクチャの固定バージョン>"
  },
  "groups": [{ "rootNode": 17, "nodes": [17, 18, 19] }],
  "checks": {
    "positionToleranceMeters": "0.000001",
    "normalUvTangentTolerance": "0.000001",
    "imageMaxChannelError": 2,
    "imageMaxChangedPixelRatio": "0.001"
  }
}
```

全オブジェクトは未知フィールドを拒否する。ID・ハッシュは既存schemaと同じ形式。ノード番号は非負整数で、固定した入力GLBに存在することを検証する。`nodes` は昇順・重複なし、グループは `rootNode` の昇順で、同じメッシュノードを複数グループへ入れない。各グループは指定rootの部分木に限る。動作設定が外部モーションを参照する場合は、既存の固定版参照をそのまま入力依存に含める。

レシピハッシュは、上のキー順・UTF-8・改行なし・空白なしのJSONの正確なバイト列に対するSHA-256。任意辞書は使わず、schema順のフィールドからシリアライズし、任意の `behavior` は存在するときだけ所定位置へ入れる。小数の閾値は例のような正規化済み10進文字列に限定する。閾値も検証方法の版もレシピに固定する。出力GLBのハッシュ・実行日時・実行先パスはレシピに含めず、循環参照と実行ごとのハッシュ変動を避ける。

同じ入力・レシピ・固定実行環境から使い捨てディレクトリで3回生成し、GLBバイト列のSHA-256一致を確認する。日時・一時パスを埋め込まず、ノード・材質・頂点の列挙順を固定する。一致しない段階では「再現可能」とせず、登録せずに原因を直す。異なる生成器や実行環境は別レシピとして扱う。

## `derivedFrom` のschema

派生アセット `schema: 2` に以下の必須フィールドを持たせる。オブジェクトは `.strict()` とし、3フィールドを必須にする。

```json
{
  "derivedFrom": {
    "id": "ship.example",
    "revision": "<64桁の入力GLB SHA-256>",
    "recipe": "<64桁のレシピSHA-256>"
  }
}
```

`id` は既存 `idSchema`、`revision` と `recipe` は `hashSchema` を使う。派生IDと正本IDの一致を拒否する。レシピの入力ID・版が `derivedFrom` と一致し、入力固定版・レシピ・出力GLBの内容ハッシュが検証できてから登録する。

読み取りは既存schema 1と新schema 2の明示的なunionにする。既存の現在台帳・固定版・インポート記録を一括変換しない。schema 1のメタデータ編集はschema 1のまま保存する。schema 2を知らない旧ツールは未知のschemaを拒否する。正本の新版・別レシピは新しい兄弟IDへ登録し、古い派生を暗黙に更新しない。

`derivedFrom` は出力GLB固定版の不変の出典情報として現在台帳・固定版・インポート記録に保持する。将来の登録・再取込・バックアップ・復元・lock/syncでも脱落させない。同一GLBの再取込で書き換えず、ユーザー編集の名前・タグ・利用先・旧版メモも保持する。循環を作らないため、最初のベイカーの入力には派生アセットを受け付けない。

派生GLBの手編集は既存IDへのreplaceを拒否し、通常の新規IDへforkする。forkは再生成可能という `derivedFrom` を引き継がず、既存の `source.scope` に元の派生ID・版と手編集した事実を記録する。名前・タグ・利用先・メモの編集は引き続き許可する。

## 統合する範囲

統合の単位は **剛体グループ × 入力材質インデックス × 頂点属性構成**。同じ見た目だけを理由に別材質を同一視しない。法線・接線・UV・頂点色などの属性構成が違うプリミティブを無理に統合しない。

剛体グループは、全クリップと動作プリセットでrootからの相対変換が不変なメッシュノードの集合。初版は構造による保守的な条件で判定する。root自身を除くrootから対象メッシュまでの経路（対象自身を含む）に、GLBのTRSアニメーションチャンネル・プリセット回転・固定した外部モーションの適用先が一つでもあれば統合を拒否する。未知の変形・制約・アニメーション拡張を含む入力も初版では拒否する。root自身やrootより上の共通の運動は、そのノードを残すことで保持する。開始フレームの隣接や有限時刻の姿勢一致を剛体性の証明に使わない。可動する帆・舵・砲架・回転部や、相対運動を持つ親子を跨ぐ指定は拒否する。各メッシュをrootのローカル座標へ変換してから材質ごとに結合し、親子の変換・アニメーションチャンネルを保持する。負の行列式に伴う面の巻き順と接線の符号も保持する。

初版は剛体の三角形メッシュだけを対象とする。skinning・morph・GPU instancing・透過描画・VFXを含む指定グループは、再生成条件が不足するため生成前に理由を返す。未指定グループは入力どおり残す。画像・材質パラメータ・サンプラー・シーン選択・カメラ・照明は変更しない。ノード名とノード番号、親子関係も残し、統合した元ノードからメッシュ参照だけを除き、統合メッシュはrootの新しい子ノードとして末尾へ追加する。

ノード番号を維持するのでGLB内のチャンネルと既存プリセットの対象がずれない。ただし派生用動作設定は新しいアセットID・出力GLB版に固定して別ハッシュで保存する。外部モーションの固定ID・版・クリップ・明示マッピングも維持し、正本の動作設定は変更しない。変換を保てない指定は自動で別グループへ推測せず、入力の不成立として返す。

## 等価性の検査

構造・幾何・レンダー比較を別々に記録する。仕様検証だけで見た目・正しいスケール・ゲーム組込みを保証しない。判定条件は登録用のデータ検証であり、ユーザーの承認状態を追加するものではない。

| 検査       | 確認すること                                                                                                                                                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 出典・保存 | 入力・レシピ・出力のSHA-256、同条件3回の出力一致、元リポジトリと正本台帳・旧版メモの内容不変                                                                                                                                                           |
| 幾何       | 既定シーンの描画三角形数が同じ。入力ノード/primitive/triangleと出力triangle範囲の対応表を生成し、重複・欠落を拒否。材質ごとの三角形数・被覆が一致                                                                                                      |
| 属性・境界 | 対応する三角形のワールド位置、法線、UV、接線、色、面の向き、境界線・包囲寸法を比較。位置はメートル単位の明示閾値、他の数値属性はレシピ閾値。材質・テクスチャ・UVセット・サンプラーは変更なしを確認                                                     |
| 動き       | 全クリップのキーフレーム時刻と各区間の中点、全プリセットの開始・中間・終了で対象ノードと三角形の位置を照合。照明・回転・外部モーションも固定条件で比較。ノード番号・チャンネル・速度・ループ条件の保持を確認                                           |
| レンダー   | 同じランタイム・カメラ・解像度・照明・色管理で、上記時刻の正面/背面/左右/上下/斜めを比較。PBRに加え法線・ワイヤーフレームも保存。例の閾値は8bit画像の最大チャンネル差2、差がある画素の割合0.1%以下。実画像で妥当性を確かめ、緩める場合も別レシピに固定 |
| 負荷       | 同じ計測器で前後のコール・描画三角形・頂点属性・展開後テクスチャを記録。三角形・画像の同一性を前提にコール削減率を示す。対象エンジン・実機のフレーム時間は別に測る                                                                                     |

姿勢とレンダーの有限サンプルは、構造による剛体判定の後の回帰比較に使う。CUBICSPLINEなどでは端点と中点が同じでもその間で動けるため、サンプルの一致だけで統合を許可しない。

元ノードから統合先triangle範囲への対応表は出典・欠落検査の補助で、制作側の部位IDを復元するものではない。統合版では部位別の660姿勢・接合対・索端検査を再実行できないため、正本として扱わない。レンダー一致も全視点・全ハードでの同等性の証明にはしない。

## 保存と導入順

恒久保存する形状は正本と「ゲームが実際に読む1形態」まで。選定前の候補は一時出力で比較し、選ばれなかったLOD・衝突・impostor等をアセットとして登録しない。レシピと計測結果・出力SHA-256だけを `catalog/recipes/results/<recipeHash>.json` に残す。結果はレシピとは別ドキュメントで、レシピのハッシュに実行結果を混ぜない。選定した出力のみ通常の `.store/` と固定版へ登録する。

新しい入力版・レシピで過去の出力を自動削除しない。既存の版・メモ・配布lockが参照する出力と復元用の完全版は保存契約を優先して保持する。「1形態」は新たに増やす形態の方針であり、履歴の削除指示ではない。`catalog/` と `.store/` の両方をバックアップする。

導入は、棚卸し（#8）→表示と版比較（#9）→この設計（#10）→固定入力1件で生成器と上記検査を実装、の順。実装時はschema互換・来歴の保存・可動部・反転変換・属性不一致・再現性・幾何欠落について使い捨てデータの回帰テストを追加し、`npm run verify` とビルド後のブラウザ検査を通す。検査結果の不足や見た目の差は元資産を変更せず報告する。
